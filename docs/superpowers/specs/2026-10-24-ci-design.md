# Design: CI on the Nix dev shell, with a signature-checked store cache

As of: 2026-10-24. Branch: `ci`. Implements issue 0011, revised by the decisions below.

## Intent

GitHub Actions runs the same commands as the maintainer's machine, with the same tools, without downloading them from upstream on every run, and without any key, secret or third-party action. Pull requests can't change what later runs restore.

## Decisions (maintainer, 2026-10-24)

1. **CI runs inside the flake's dev shell on the Ubuntu runner**, not with setup-node, apt and pip. GitHub has no NixOS runners; Nix is installed on `ubuntu-24.04`. The image is pinned so that every job runs on the same one while `ubuntu-latest` moves to 26.04 (19 October to 19 November 2026); moving on is a deliberate change (issue 0022). A small shell `devShells.ci` holds what `check` needs (Node.js 24, Valgrind, REUSE); the default shell keeps everything else.
2. **Nix is installed from a release tarball**, single-user (`./install --no-daemon --no-channel-add`), checked against a SHA-256 pinned in the repository. GitHub's cache keeps the tarball. No installer action is used: each one either skips the hash check, installs another Nix, runs an unpinned installer, or downloads unverified archives.
3. **The installed Nix is the one the pinned nixpkgs ships** (`nixpkgs#nix.version`, 2.34.9 today, a fixed release of the 13 October 2026 advisory). CI fails with instructions when `flake.lock` moves to a nixpkgs with another Nix, so `flake.lock` is the single source of both versions.
4. **The dev shell comes from a `file://` binary cache** kept in GitHub's cache. `nix copy` writes each path's original `cache.nixos.org-1` signature into the cache's `.narinfo` files. Reading jobs keep `require-sigs = true` and trust only the default key, so a path whose content was altered is rejected (checked locally on 2026-10-24: a removed signature, a changed `NarHash` and a changed NAR byte with a recomputed file hash were all refused). The shell's own `-env` output is unsigned and is rebuilt on each run. Nix also downloads the paths nixpkgs marks as not worth downloading (`always-allow-substitutes = true`), such as the `nodejs_24` wrapper: built on the runner they would carry no signature (E1 found it on 2026-10-24). cache.nixos.org stays a lower-priority fallback. This protects the store content only: restoring a cache entry can write any file the runner can write (`actions/cache` extracts with absolute paths), before Nix or the tarball check looks at it. A poisoned entry is kept out only by decision 5.
5. **Only one job writes caches**: `seed-cache.yml`, on pushes to `main` that change the dev shell or the lockfile, weekly, and by hand. It restores nothing, takes everything fresh from cache.nixos.org, releases.nixos.org and the npm registry, runs no project code and no pull-request code, and saves the tarball, the store cache and the npm cache. Every other workflow sets `cache-mode: read` (or `none`), which GitHub enforces with scoped tokens (generally available since 2026-09-10).
6. **Dependabot updates `flake.lock`** monthly, like npm (`package-ecosystem: nix`, version updates only, since 2026-04-07). Moving to the next release branch stays a manual change in `flake.nix`.
7. **CI fails halfway through the overlap of two releases.** NixOS supports each release for seven months: a YY.05 release until 31 December of that year, a YY.11 release until 30 June of the next; the successor comes out at the end of November or May, so the two overlap by about a month. `npm run nixos-release` reads the branch from `flake.lock`. From the first of the last month (1 December, 1 June) it warns that the successor is due; from the 16th of that month, or for a branch that isn't `nixos-YY.05`/`nixos-YY.11`, it fails. The maintainer chose the earlier failure point so that the project moves while the old release is still supported. It runs in `check` and in a read-only job of the weekly seed workflow (a failed scheduled run makes GitHub email the maintainer), not in `npm run check`, so an old commit checked locally doesn't fail because of today's date.

8. **`check` always runs in full**, on every pull request and every push to `main`: no path filter and no detection of what changed. CI time matters less than a simple, predictable check, and a required status check from a workflow skipped by a path filter would stay "pending" and block the merge. Today the full check takes about 3 minutes locally, almost all of it the perf gate; for the finished app about 6–8 minutes locally and 8–12 minutes in CI are expected.

## Proposals made in this design (approved with the plan)

- **The perf gate in CI** follows the measurement on the runner (experiment P below):
  - If every scenario on every sampled runner is within ±1 % of `tests/perf/baseline.json`, CI compares with the checked-in baseline, exactly as locally.
  - Otherwise CI measures the pull request and its merge base in the same job, and allows per scenario the base's count times the ratio of the two commits' baselines, plus 5 % (issue 0011's proposal; the Ubuntu Valgrind part of it no longer applies).
- `actionlint` (from nixpkgs, run with `nix run`, not added to the project) checks the workflow files before they are pushed.

## Components

| File | Responsibility |
| --- | --- |
| `flake.nix` | `devShells.ci` (`mkShellNoCC` with Node.js 24, Valgrind, REUSE); the default shell includes the same list |
| `.github/actions/nix/action.yml` | local composite action: restore (or download) the tarball, check its SHA-256 (`verify-tarball.sh`), install single-user, write `nix.conf` (without the global flake registry), restore the store cache and add it as a substituter, check the Nix version against `flake.lock` (`check-version.sh`); defines the three cache keys |
| `.github/workflows/seed-cache.yml` | the only writer of caches (decision 5): `cache-mode: read` for the workflow, `write` only on the seed job; plus a separate read-only job for the weekly release check; also callable (`workflow_call`) |
| `.github/workflows/check.yml` | `npm run check` (lint, type check, tests, perf gate, REUSE) and the release check, always in full; `cache-mode: read`; also callable |
| `.github/workflows/dependency-review.yml` | GitHub's `dependency-review-action` on pull requests that change `package-lock.json`; `cache-mode: none` |
| `.github/workflows/ci-experiments.yml` | temporary: the experiments below, removed before the branch is handed over for merging |
| `scripts/nixos-release-status.ts`, `scripts/nixos-release.js` | the supported-release check (pure function, CLI) |
| `.github/dependabot.yml` | adds the `nix` ecosystem |

## Hosts the CI contacts

| Host | When | Integrity |
| --- | --- | --- |
| GitHub Actions cache | every run | none of its own: Nix signatures and hashes, the pinned tarball hash, npm's lockfile integrity |
| releases.nixos.org | seed run; tarball cache miss | SHA-256 pinned in the action |
| cache.nixos.org | seed run; fallback on a miss | `cache.nixos.org-1` signature |
| github.com | the nixpkgs source in the seed run, and in every run unless the store cache can serve it (experiment E4) | `narHash` in `flake.lock` |
| registry.npmjs.org | seed run; npm cache miss | `integrity` in `package-lock.json` |

## Experiments before relying on it

One push of the branch runs all of them (`ci-experiments.yml`); each job writes PASS or FAIL lines into the run's summary.

| Id | What | Passes when |
| --- | --- | --- |
| E1 | signatures survive `nix copy` | every narinfo has a `cache.nixos.org-1` signature except the `-env` output and content-addressed paths |
| E2 | a warm run is self-sufficient | with only the file cache as substituter and cache.nixos.org and releases.nixos.org blocked in `/etc/hosts`, `nix develop .#ci` succeeds and builds only `-env` |
| E3 | altered content fails closed | a changed NAR byte, a changed `NarHash`, a removed `Sig:` line and a changed `-source` NAR are each refused; a changed tarball stops the install |
| E4 | the nixpkgs source comes from the cache | E2 also succeeds with github.com blocked; if not, github.com stays a per-run host |
| E5 | cache scoping is enforced | on the pull request and on push, a save in a `cache-mode: read` job doesn't create the entry and one in a `write` job (the control) does; the seed job, a job-level `write` in the `read` workflow `seed-cache.yml`, saves |
| P | perf counts on the runner | three runner jobs report every scenario's change against the baseline and the CPU model (decision rule above) |
| T | timings | cold (seed), warm and uncached (the pull request's first `check`) job times |

## Out of scope

Build and size check, the `templates`, `e2e` and `release` workflows (with their branches); NixOS/nix-installer (revisit when Hydra builds it, proposed from Nix 2.36); the switch to nixos-26.11 (issue 0021).

## Research

The research behind this design (24 October 2026) found that uncached runs add about 3 × 10⁻⁶ to cache.nixos.org's weekly traffic and that NixOS publishes no fair-use limit for CI, so caching here is a courtesy and makes CI independent of upstream outages. Hosted caches (Cachix, FlakeHub, Magic Nix Cache, Attic and others) either skip upstream paths, need a secret, OIDC or extra permissions, re-sign with their own key, or download unverified binaries. Sources: [NixOS cache blog 2026](https://nixos.org/blog/stories/2026/nix-binary-cache/), [S3 sponsorship 2025](https://discourse.nixos.org/t/2025-s3-sponsorship-more-resources-for-a-sustainable-nix/67019), [Nix security advisory October 2026](https://discourse.nixos.org/t/security-advisory-for-nix-and-lix-october-2026/80547), [GitHub: cache-mode](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode/), [GitHub: Dependabot Nix](https://github.blog/changelog/2026-04-07-dependabot-version-updates-now-support-the-nix-ecosystem), [TanStack postmortem](https://tanstack.com/blog/npm-supply-chain-compromise-postmortem), [NixOS 26.05 announcement](https://nixos.org/blog/announcements/2026/nixos-2605/).
